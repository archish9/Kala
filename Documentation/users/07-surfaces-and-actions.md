# Surfaces and actions

Two vocabularies kala understands: the kinds of **screen** it knows the requirements for,
and the design **actions** you can ask it to take.

---

## Surfaces (6)

A **surface** is one screen a user lands on — a route, a page, a top-level view. Not a
component, not a file.

Ask kala for a surface brief before building a screen and it tells you which states that
kind of screen must handle — the ones that get skipped and then break on real data.

Say: *"What states does the settings page need?"*

A brief has two halves that behave differently:

| Half | Contents | Checkable? |
|---|---|---|
| `requiredStates` | The states this kind of screen must handle | **Yes** — the same vocabulary the rules use |
| `requirements`, `antiPatterns` | What it must do and avoid | No — judgement you satisfy |

That first half is what turns "handle real-world states" from advice into something kala can
later check. The brief says a settings screen needs an `error` state; the
`missing-error-state` rule then checks one exists.

### Naming a surface

Three forms all work:

```
"settings"                      the id
"sign-in"                       an alias → auth
"src/app/settings/page.tsx"     a route path → settings
```

Route paths are reduced to their most meaningful segment, so `.../settings/page.tsx` matches
`settings` rather than `page`.

**Required states** are machine-checkable: after you build the screen, `verify` checks that
those states actually exist in the code.

## Actions (13)

Ask for one of these and kala returns a playbook grounded in *your* project — the real type
scale, the real spacing values, and the things your chosen system bans.

Say: *"Make the pricing page bolder"* or *"Harden the checkout form"*.

| Action | What it does | Grounded in |
|---|---|---|
| `adapt` | Make the surface work at the sizes it will actually be used at. | `space`, `type` |
| `animate` | Add motion that carries meaning, and only where it earns its cost. | `motion` |
| `bolder` | Amplify a design that reads as safe or timid, without abandoning the system. | `type`, `color`, `space` |
| `clarify` | Rewrite interface copy so it says what happens, in the user's words. | `type` |
| `colorize` | Introduce colour with intent into a surface that is flat or monochrome. | `color` |
| `delight` | Add one memorable moment where it costs the user nothing. | `motion`, `color` |
| `distill` | Remove everything that is not carrying weight, until what remains is obvious. | `space`, `type` |
| `harden` | Make a surface survive real data, real networks, and real people. | `space`, `type`, `color` |
| `layout` | Give the surface a spatial structure a reader can predict. | `space` |
| `onboard` | Design the first run, when there is no data and no habit yet. | `space`, `type`, `color` |
| `optimize` | Reduce what the browser has to do before the surface is usable. | `motion` |
| `quieter` | Calm a surface that overstimulates, by removing emphasis rather than shrinking it. | `type`, `color`, `motion` |
| `typeset` | Fix hierarchy, measure, and rhythm in the text itself. | `type`, `space` |

**Grounded in** lists which of your project's token groups the answer is built from. This is
why the same action gives two projects different answers.

### Three worth knowing about

**`animate`** opens with a frequency gate: *ask how often the user triggers this.*
High-frequency interactions get faster motion, or none at all. It closes with: *honour
`prefers-reduced-motion` by removing motion, not by shortening it.*

**`harden`** is the checklist version of the state rules: render every reachable state; test
each text container with a value three times longer than the design assumes; give every
control a disabled and a pending appearance.

**`clarify`** is about copy: *make button labels name the outcome* — "Save changes", not
"Submit"; "Delete project", not "OK".

### Why the grounding matters

The playbook text is generic. The **answer is not**.

```
"Make it bolder" on a dense analytics dashboard
  → system: quiet-precision
  → type steps to work within: 12, 13, 15, 18, 22, 26, 31
  → banned here: card-in-card · gradient-anything · shadow-on-rest-state

"Make it bolder" on a kids education app
  → system: playful-rounded
  → type steps to work within: 12, 14, 17, 21, 27, 33, 42
  → banned here: dense-data-grid · all-caps-labels · tiny-tap-targets
```

Same action, different answers, because kala reads your project's lock rather than replying
from a fixed script.
